# ISSUE-1: Pegout signed with another pegout's input amounts during federation migration, freezing the withdrawal and stalling the peg

## Pipeline Result
**Verdict**: VALID
**Final Severity**: High
**Original Claimed Severity**: Not labeled (report describes "temporary freezing of funds on the peg-out side + halt of pegout processing and of the federation change")
**Pipeline Exit Point**: Step 4 (full adversarial pass; no early exit)
**Confidence**: HIGH

## Summary
`ReleaseCreationInformation.decodeUtxoOutpointValues()` selects the segwit BIP143 input amounts with `.findFirst()` over the `pegout_transaction_created` logs, matching only the event-signature topic (`topic[0]`) and never the pegout's `btcTxHash` (`topic[1]`). When one `updateCollections` receipt carries two such events (a migration pegout emitted first, a batched user-withdrawal pegout second), the batch pegout is signed with the migration pegout's amounts. Segwit commits the input amount, so the signature is invalid, the withdrawal freezes in `pegoutsWaitingForSignatures`, and — when a migration pegout and a batch pegout share one `updateCollections` and the buggy one is promoted first — the rskj collision guard reverts every subsequent `updateCollections`, halting the peg and stalling migration. Every claim was verified against the actual `powpeg-node` and bundled `rskj` source. Valid; severity capped at High by full recoverability (patch + re-sign, no consensus change).

## Justification
The initial sweep confirmed the defect directly by reading the source: the filter checks `log.getTopics().get(0)` only and `.findFirst()` returns event[0] regardless of which pegout is being signed. Three parallel adversarial checkers then verified every downstream and upstream claim against the real code:

1. **Propagation (confirmed).** The mis-selected amounts flow, unchanged and mutually consistent, into the BIP143 `prevValue` (`SegwitSigHashCalculatorImpl.calculate`, `prevValue = releaseOutpointsValues.get(inputIndex)`) and into the HSM `OUTPOINT_VALUE` field. Both the signed sighash and the amount handed to the signer come from the same wrong list.
2. **Asymmetry (confirmed).** `getInformationFromEvent` already filters `release_requested` by both `topic[0]` (signature) and `topic[2]` (btcTxHash). The codebase demonstrably knows the correct correlation; the amount path simply omits it. The `pegout_transaction_created` btcTxHash is available at `topic[1]` and is ignored.
3. **Reachability (confirmed).** `updateCollections` runs `processFundsMigration` then `processPegoutRequests` then `processConfirmedPegouts`; the migration and batch paths both reach `logPegoutTransactionCreated` via `settleReleaseRequest → processReleaseTransactionInfo`, appending to the same per-transaction log list → one receipt, migration event first. No mutual exclusion prevents co-occurrence (migration drains the *retiring* federation; withdrawals pay from the *active* federation — disjoint state). On mainnet the migration window is ~10,585 blocks (extendable to 172,800) spanning thousands of `updateCollections`, while withdrawals batch every 360 blocks — overlap is expected, not a corner case.
4. **Segwit/mainnet (confirmed).** The segwit sighash path is taken per-input when the input carries a witness; P2SH-P2WSH ERP federations (RSKIP305 / `reed800`, mainnet block 8,052,200) populate witnesses. A wrong amount yields a signature valid over the wrong sighash and invalid against the real UTXO — funds frozen, never stealable. Legacy federations don't commit the amount and are unaffected.
5. **No recovery (confirmed).** Amounts are re-derived from the immutable receipt on every attempt; `.findFirst()` is deterministic; no re-derivation/correction/retry path exists. The freeze persists until the code is patched.
6. **Cascade (confirmed, with nuance).** `pegoutsWaitingForSignatures` is a `Map<Keccak256,BtcTransaction>` keyed by the creation rskTxHash (RSKIP375, active mainnet). Two pegouts created in one `updateCollections` share that key. The guard `checkIfEntryExistsInPegoutsWaitingForSignatures` throws on collision; the throw propagates out of `Bridge.updateCollections` as `VMException` and rolls back the entire call (no isolation); the maps have no expiry, so the halt is permanent once triggered.

**Impartiality note on the cascade.** The collision is an *independent* rskj structural condition (same-creation-hash key under RSKIP375), and in normal operation it is transient/self-healing: the first pegout is signed and removed via the separate `addSignature` path, freeing the key before the second is promoted. The signing bug's contribution is to make the first-promoted pegout permanently unsignable, converting the transient collision into a permanent halt — **but only** when (a) a migration pegout and a batch pegout co-occur in one `updateCollections`, and (b) the buggy pegout is promoted first (promotion order is set by `BTC_TX_COMPARATOR` over serialized tx bytes, not controlled by the bug). If the good pegout sorts first, it clears the key and only that single withdrawal freezes — no bridge/migration halt. The report scopes the halt to the co-occurrence case but does not mention the promotion-ordering condition; this is a minor completeness gap, not an invalidation. The **guaranteed, unconditional** impact given a two-event receipt is a single frozen user withdrawal (burned RBTC, undeliverable BTC); the peg-halt is the worse-case subset.

**Robustness to the one external unknown (PowHSM).** The report's claim that the PowHSM only range-checks the host-supplied `outpointValue` (rather than re-deriving it) could not be verified from in-scope code (rsk-powhsm is a separate repo). It does not matter to the verdict: if the HSM trusts the amount, the federator emits an invalid signature; if the HSM re-derives and refuses, no signature is produced. Both outcomes leave the batch pegout unsignable and frozen. The finding is robust either way.

**Severity.** No privileged role is required (Step 2: attack path uses ordinary withdrawal traffic during a scheduled, recurring migration; also deliberately griefable by any user at no profit). Impact is a temporary freeze of user funds plus a (conditional) halt of the peg-out side and of federation rotation. It is **recoverable** without a hard fork or consensus change: after the one-line btcTxHash filter is added, federators re-derive the correct amounts, re-sign the stuck pegout, the collision clears, and processing resumes. Recoverability caps this below Critical. It exceeds Medium because real user funds are frozen, no special access is needed, it fires on ordinary traffic during recurring operations, and it can stall a security-motivated federation rotation. → **High**. (Programs whose scale rates any live-bridge halt / temporary fund freeze as Critical regardless of recoverability could rate it Critical; the hinge is purely the recoverability treatment.)
